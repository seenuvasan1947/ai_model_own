# v6 Changes: Proper Language-Substrate Training

v5 validated the vertical-stack architecture (Layer 1 substrate + Layer 2 + Layer 3 memory) with sparse growing units and distributed activation. **The architecture works.** What doesn't work yet is output quality — and the root cause was correctly identified: **Layer 1 was trained on the wrong kind of data.**

v1-v5 trained Layer 1 on *Alice in Wonderland* + *Sherlock Holmes* — literary novels. That taught Layer 1 to write "Victorian mystery narrative prose," not to be an English master. When you feed a Sherlock-flavored Layer 1 into a memory system, no memory architecture can overcome the fact that the underlying language module doesn't know general English — it knows one specific literary register.

v6 fixes this. **Nothing about the architecture changes.** The stack, the memory layers, the update rules, the recall mechanism — all identical to v5. Only three things change: **what Layer 1 learns from, how big Layer 1 is, and how we measure success.**

---

## Post-Design Correction — Facts Removed from Layer 1 Training

The first draft of v6's synthetic data included world-facts (capitals of
countries, planets in the solar system, "the sky is blue", "cats have four
legs"). That was wrong and got caught before training: **specific facts do
not belong in Layer 1's frozen weights**, because Layer 2/3 exists precisely
to hold facts that can be added, updated, and forgotten over time. Baking
facts into Layer 1 defeats the whole continual-learning design.

Removed from Layer 1 training corpus:
- Capitals of countries
- Planet names / solar-system facts
- Color-of-specific-things ("the sky is blue", "grass is green")
- Animal-attribute facts ("a cat has four legs")

Kept in Layer 1 training corpus (these are LANGUAGE, not facts):
- Number words and arithmetic syntax ("three plus four is seven")
- Day/month names and their canonical order (closed vocabulary, like tense forms)
- Opposites as closed English word-pairs (hot/cold, big/small, ...)
- Grammar patterns (tense, negation, questions, plurals, sentence shapes)

Corresponding change to evaluation:
- `data/eval_qa.jsonl` — language-competence questions ONLY (arithmetic,
  opposites, day/month sequence, plurals). Tests Layer 1 alone.
- `data/eval_qa_continual.jsonl` — world-fact questions PAIRED with the fact
  to feed into memory first via `continual_read.py`. Run by `eval_qa_continual.py`.
  Tests the memory stack.

Rule of thumb applied throughout: **if the answer could change per-user
or per-time-period, it belongs in Layer 2/3, not Layer 1.**

## What Changed vs. v5

### 1. Layer 1 training corpus — domain-neutral English master, not literary specialist

| Data source | Purpose | Approximate size |
|---|---|---|
| **TinyStories** (public HuggingFace dataset) | Simple, grammatically clean English designed to teach small language models coherent generation | **~30M words** (subset, bumped from 10M -- see corpus-bump note below) |
| **Simple English Wikipedia** | Neutral factual/expository prose, common vocabulary, natural in-context number usage | **~15M words** (subset, bumped from 5M) |
| **Synthetic grammar/number/facts data** (generated by `gen_synthetic.py`) | Number literacy, days/months/colors, common facts, canonical sentence patterns — the "grammar textbook" content | ~100K-500K tokens |
| **Q&A behavior set** (expanded from v5's `qa_behavior.txt`) | Question → answer response pattern (the *skill* of answering, not knowledge) | ~5K-20K tokens |

**Deliberately excluded from Layer 1 training:** Alice, Sherlock, any single-author literary text, informal internet text (Twitter/Reddit), any domain-specific content. Those belong in Layer 2/3, fed at read-time via `continual_read.py` — NOT baked into Layer 1's weights.

**Why this matters:** if Layer 1 memorizes one author's style, it can only generate in that style. If Layer 1 learns *general English*, it can generate about *anything* that Layer 2/3 later stores. This is the whole point of having a substrate/memory split.

### 2. Layer 1 size scaled to match corpus

v1-v5 used a 1.37M-parameter model — vastly too small for its corpus and overfit accordingly. v6 scales appropriately:

| Setting | v5 | v6 |
|---|---|---|
| n_embd | 128 | **256** |
| n_layer | 3 | **6** |
| n_head | 4 | **8** |
| context_size | 64 | **256** |
| Parameters | 1.37M | **~10-15M** |
| Vocab size | 6000 | **8000-12000** (rechecked against new corpus) |

Bigger model + much bigger corpus = memorization becomes structurally harder than generalization. Should measurably help the overfitting problem v4's held-out val split revealed.

**Corpus-bump note (added post-design):** The initial v6 target was ~15-20M
total words. Bumped to ~45-50M (30M TinyStories + 15M Simple Wiki + 44K
synthetic + Q&A) once we agreed: since we're doing one long training run
anyway, spending an extra 30-45 min of download time to double the real-text
data is worth it. Rationale:
- Bigger real corpus = better vocabulary coverage (roughly doubles the number
  of rare words the model sees enough times to learn).
- Bigger real corpus = grammar patterns show up in more natural distributions,
  including constructions synthetic doesn't cover (passive voice, subordinate
  clauses, conditionals, reported speech).
- Bigger real corpus = numbers appear more often in natural context ("10 cars
  stolen", "third chapter", "twice as many"), teaching number-in-context, not
  just synthetic arithmetic templates.
- Ratio of ~3-4 tokens per parameter (45M / ~12M) is a healthy training regime
  vs. ~1 token per parameter at the smaller size, which was overparameterized.

Corresponding config bumps: `max_iters` 40K -> 70K to actually use the larger
corpus. Full training time estimate rises from 2-8 hours to 4-14 hours; see
HOWTO_TRAIN_TEST.md.

### 3. Held-out Q&A evaluation harness (new)

v4 added a held-out **token-level** val split (`val_split=0.1`), but there's still no way to measure "does the model actually answer questions correctly, and does memory help?"

v6 adds `eval_qa.py`:
- Loads a small test set of question→expected-answer pairs (never seen during training)
- Runs each question through `ask.py` in two modes: memory ON, memory OFF
- Scores by keyword overlap between generated and expected answers
- Reports both scores + the memory-on-vs-off delta

This lets us **quantitatively answer**: does the memory stack actually improve answering? Every prior version could only guess.

### 4. Early stopping on Layer 1 training (new)

v1-v5 always trained for a fixed `max_iters`, even after val loss started rising. v6's `train_layer1.py` tracks the best val loss seen so far and saves that checkpoint as `layer1_final.pt` — automatically stopping the effective training at the point of best generalization instead of the point of worst overfitting.

Configurable via `TrainConfig.patience` (steps of no improvement before considering training "done"). Default: 5 evaluation checkpoints without improvement.

### 5. Corpus preparation scripts (new)

- `data_prep/download_tinystories.py` — pulls TinyStories via HuggingFace, subsets it to a target token count.
- `data_prep/download_wikipedia.py` — pulls Simple English Wikipedia via HuggingFace, cleans and subsets.
- `data_prep/gen_synthetic.py` — generates the synthetic grammar/number/facts corpus programmatically.
- `data_prep/build_corpus.py` — combines all four sources into `data/foundation_corpus.txt`.

These are runnable independently, and `HOWTO_TRAIN_TEST.md` documents the sequence.

## What DIDN'T Change vs. v5

- **The stack architecture** (Layer 1 above L2 above L3, vertical). Same as v5.
- **The unified memory update rule** (strengthen + decay + prune, one rule per layer, different rate constants). Same as v5.
- **Sparse growing units + distributed activation.** Same as v5.
- **Recall mechanism** (L2 + L3 activations projected back into Layer 1's residual stream). Same as v5.
- **No backprop below Layer 1.** Same design constraint since v1.
- **Layer 1 frozen after training.** Same as v5.

If v6's larger, better-trained Layer 1 produces coherent English but memory-injected recall still doesn't yield correct Zeta-like answers, that would be architectural evidence and we'd revisit. But we can't judge the architecture properly until Layer 1 itself is competent — and v1-v5's Layer 1 never was.

---

## What v6 Is Explicitly Not Trying to Do

- **Match GPT/Claude quality.** Not the goal, never was. Goal is a small, self-hosted, brain-inspired system that genuinely learns after training.
- **Solve the "learned integration between Pair 1 and memory" gap** (the residual-stream splice is still not something Layer 1 was *trained* to expect). That's future work, and the honest reason for deferring: we still can't tell if it needs solving until Layer 1 is competent enough that memory recall could plausibly steer generation coherently.
- **Real-time training / no-restart continual learning of Layer 1 itself.** Layer 1 stays frozen. Only Layer 2/3 change online.

---

## Success Criteria for v6

1. **Val loss stays close to train loss** (< 0.5 gap) at the point Layer 1 is saved. This confirms it actually generalized instead of memorizing.
2. **Ablation shows memory helps.** `eval_qa.py`'s memory-on score is measurably higher than memory-off. If they're equal, the memory pathway isn't contributing anything useful.
3. **Generated English is coherent** on generic prompts (not domain-specific). If you ask "What color is the sky?" the answer is "The sky is blue." or similar — not word salad, not Sherlock-flavored gibberish.
4. **Continual learning still works.** After feeding a new story via `continual_read.py`, memory-on generation should differ from memory-off on questions about that story.

Not required for success (tracked but not gating): overall answer quality relative to any external baseline. This is still a small research prototype, not a product.
